# Installation Path SideFX Houdini 22

In Distrobox (Debian 12) on openSUSE Tumbleweed (Wayland) with independent HOME.


Host System: openSUSE Tumbleweed (KDE Plasma, Wayland)  
Container Environment (Guest): Debian 12 (Distrobox / Podman / Rootless)  
Hardware: NVIDIA GeForce RTX 5080 (Blackwell) | Kensington Trackball  

---

## STEP 1: HOST FIREWALL CONFIGURATION. SINGLE-TIME SETUP PER COMPLETE INSTALLATION.

OBJECTIVE:
Enable the necessary TCP ports for local license communication before initializing 
any container. The dynamic firewall of openSUSE (firewalld) blocks these incoming 
connections by default. This step is a one-time operation, and if the containers 
become corrupted, you do not need to modify these parameters on the host again.

OFFICIAL SIDEFX THEORY:
SideFX establishes that the license server (sesinetd) requires TCP port 1715 
and the client proxy (hserver) requires TCP port 1714. It assumes an open local 
network environment without strict restrictions between subprocesses. It contemplates 
a direct installation on the system.

THE TECHNICAL REALITY IN DISTROBOX:
Since Distrobox/Podman Rootless shares the network stack directly with openSUSE, 
any internal request from Houdini is filtered by the host's firewall. If these 
ports are not opened on the host before starting, the container will remain 
isolated and unable to validate any license.

COMMANDS TO EXECUTE ON THE HOST (OPENSUSE):

1. Identify the active network zone of the firewall (normally returns 'public')

sudo firewall-cmd --get-active-zones

2. Permanently open the license ports in the active zone

sudo firewall-cmd --zone=public --add-port=1715/tcp --permanent
sudo firewall-cmd --zone=public --add-port=1714/tcp --permanent

3. Reload the service to apply changes immediately

sudo firewall-cmd --reload

CONSOLE VERIFICATION:

sudo firewall-cmd --zone=public --list-ports

SUCCESS: The result must explicitly include: 1714/tcp 1715/tcp

## STEP 3: CREATION OF THE DISTROBOX CONTAINER WITH PERSISTENCE AND PERMISSION RULES, AND COPYING THE INSTALLER.


OBJECTIVE:
Initialize the Debian 12 container and apply POSIX permissions over the generated files.

COMMANDS TO EXECUTE ON THE HOST:

1. Create the distrobox

distrobox create --name houdini --image docker.io/library/debian:12 --volume /mnt/virtuality:/mnt/virtuality --home /mnt/virtuality/houdini/home --nvidia --hostname "$(hostname)" --yes

#### NOTES:
--volume /mnt/virtuality:/mnt/virtuality
Directly and bidirectionally maps the partition of your real hard drive inside the container, respecting the same absolute path. This is vital to avoid broken symlinks and allow projects or caches to be written directly to massive external physical storage.

--home /mnt/virtuality/houdini/home
Reroutes the container user's root directory ($HOME) away from Podman's default path, forcing it to save in the desired location. By default, the container shares HOME with the host. This guarantees that all Houdini customization (preferences, scripts, tool shelves, plugins, and configurations) survives intact if the Distrobox container is removed or recreated in the future.

--nvidia
Critical instruction that duplicates and injects the host's NVIDIA driver binary modules (including CUDA, OptiX, and OpenGL) directly inside the box. Without this flag, the GPU would remain invisible, leaving Houdini without hardware acceleration and causing the 3D Viewport or the Karma engine to collapse due to lack of compute capability.

--hostname "$(hostname)"
Clones the network hostname of your openSUSE machine exactly inside the Debian container. It is a mandatory bypass for Houdini licensing: SideFX's cryptographic validator strictly compares the server hostname with the client's, and any discrepancy or autogenerated name by Podman would break the network handshake, invalidating licenses.

--yes
Automation flag that accepts all download and initialization terms by default, avoiding interactive pauses in the terminal during the automatic deployment of the container skeleton.

2. Enter the container for the first time

distrobox enter houdini

Initializes the container environment, maps host user permissions (UID/GID), and populates internal file paths.

Note: Must be executed before modifying permissions, setting up Vulkan/license configs, or copying installation files. Otherwise, paths and user mappings will be invalid.

3. Ensure total ownership of the structure for the real user

sudo chown -R $USER:$USER /mnt/virtuality/houdini

4. Apply selective POSIX permissions (Navigable folders and non-executable files)

find /mnt/virtuality/houdini -type d -exec chmod 755 {} +
find /mnt/virtuality/houdini -type f -exec chmod 644 {} +


CONSOLE VERIFICATION:

ls -ld /mnt/virtuality/houdini/home
ls -ld /mnt/virtuality/houdini/workspace

Both must return exactly: drwxr-xr-x and the ownership of your host user.

distrobox list

Must list the container 'houdini' with status created or active.

#### ARCHITECTURE NOTES (THEORY VS. REAL PRACTICE):

Why does the strict order of permissions go here? 
When creating the container, Rootless Podman creates the hidden skeleton files of the Debian system (such as the initial .bashrc) inside the persistent '/home' folder. Executing 'chown' and 'find' at this exact moment guarantees that everything created internally falls under your absolute control and free of write blocks.

The myth of 'chmod 777': Forcing universal permissions opens security breaches and destabilizes persistence. The combined use of 'chown' with '755' and '644' keeps Rootless Podman policies intact and the environment clean.

## STEP 4: THE GRAPHICS LIBRARIES SHIELD (INSIDE THE DEBIAN 12 CONTAINER)

OBJECTIVE:
Massively and cumulatively install the full stack of graphics dependencies, X11, Qt6, and diagnostic tools that the base image of Debian 12 does not include by default, shielding the environment against silent startup errors.

COMMANDS TO EXECUTE INSIDE THE CONTAINER:

1. Enter your created container with alias

houdini

2. Update the Debian internal repository list

sudo apt update

3. Install the cumulative block of dependencies

sudo apt install -y libasound2 libc6 libcups2 libcurl4 libdbus-1-3 libdrm2 libegl1 libexpat1 libfontconfig1 libgcc-s1 libgl1 libglib2.0-0 libglu1-mesa libglx0 libice6 libncursesw6 libnspr4 libnss3 libopengl0 libpci3 libsm6 libxcb-cursor0 libxcomposite1 libxrender1 libxrandr2 libxcursor1 libxi6 libxtst6 libxkbcommon0 libxss1 libatomic1

4. Install specific integration libraries for the Qt6 Backend

sudo apt install -y libxkbcommon-x11-0 libxcb-icccm4 libxcb-image0 libxcb-keysyms1 libxcb-render-util0 libxcb-xinerama0 libxcb-xinput0 libxcb-xfixes0 libxcb-shape0 libxcb-randr0 libxkbfile1

5. Install native Vulkan and Network diagnostic tools

sudo apt install -y vulkan-tools libvulkan1 libvulkan-dev mesa-vulkan-drivers spirv-headers netcat-openbsd

#### FIELD NOTES (THEORY VS. REAL PRACTICE):

- The Missing Libraries Shield: Debian images in Distrobox come ultra stripped-down for servers. Even though SideFX's official documentation assumes a full desktop Linux operating system, if you try to launch Houdini 22 without this block, the terminal will throw fatal errors of type "cannot open shared object file" or silently crash at startup.

- Critical Qt6 Packages: Houdini 22 migrated its native interface to Qt6. Packages like 'libatomic1' (for framework compilation) and the 'libxcb-*' integration libraries are indispensable for the graphics backend to render floating windows correctly without breaking the session.

- libpci3 and libvulkan1 allow resolving the graphics drivers injected by --nvidia correctly.
- netcat-openbsd is useful for diagnosing local ports if `hserver` fails.

/mnt/virtuality/houdini/workspace/houdini-22.0.368-linux_x86_64_gcc14.2/

COMMANDS TO EXECUTE INSIDE THE CONTAINER (DEBIAN 12):

1. Navigate to the uncompressed installer folder in the Workspace

cd /mnt/virtuality/houdini/workspace/houdini-22.0.368-linux_x86_64_gcc14.2/

2. Launch the official interactive installer with administrator privileges

sudo ./houdini.install

3. During the terminal installation wizard:

a) Accept the license terms (Type 'yes').
b) Install the required components (Houdini, License Server, Desktop Icons, SideFx Labs).
c) Confirm the default installation path: /opt/hfs22.0

#### FIELD NOTES (THEORY VS. REAL PRACTICE):

- SideFX documentation dictates always installing to '/opt/hfsX.X'. By doing so inside the container, the software is written into Debian's isolated root, but thanks to your '$HOME' being rerouted to the external hard drive, your personal configurations will never touch the openSUSE partition.
- The myth of "losing the installation if the container is deleted": In Distrobox architecture, if you remove the container, the files in '/opt/hfs22.0' are indeed deleted because they belong to the guest OS. However, this is intentional to keep the Host clean. Rebuilding the environment takes less than 5 minutes following this guide, since the physical installer remains safe in your physical 'workspace'.

## STEP 6: HOUDINI_SETUP

A. Wake up the licensing daemon

sudo service sesinetd start

If the above command returns an error due to the absence of a modern init system (like systemd) in Distrobox rootless environments, invoke the direct path to the legacy script provided by SideFX:

sudo /etc/init.d/sesinetd start


B. Initialize the Houdini Environment

By default, Houdini is installed in path /opt/hfsXX.X/. For the terminal and the operating system to recognize the program commands and libraries, the manual indicates executing:

cd /opt/hfs22.0

source houdini_setup

This shell script configures the session environment variables (such as PATH, HOUDINI_PATH, and PYTHONPATH) and prints confirmation that the Houdini environment has been properly initialized.

SUCCESS: The Houdini 22.0.368 environment has been initialized.

ORIGINAL ERROR AND SOLUTION: When running source houdini_setup and attempting to launch any binary or graphical interface, clean Linux base images (like Debian 12 in container) do not include by default all dynamic libraries for Qt6, X11, or audio that compiled Houdini binaries require to boot (libsmime3.so, libatomic1, etc.). To prevent this, all possible dependencies were installed from the start.

D. Turn on the client licensing proxy to open the communication channel

hserver

When running this command, the terminal will display consecutive warnings: 

"sh: 1: systemctl: not found". 

This behavior is irrelevant and safe to ignore; hserver attempts to check if the service is running under systemd and, finding none due to container limitations, falls back to scanning memory processes where it will successfully detect your previous manual initialization.

### NOTE: 
Before opening the graphical interface, the SideFX ecosystem requires two background services to be operational: sesinetd (Houdini License Server): The daemon that manages and validates licenses in the background, and hserver (Houdini Server): The proxy through which the Houdini application communicates with sesinetd.

On a standard native Linux installation, the installer registers sesinetd as a system service to start automatically.

Firewall errors resolved in step 1:
When hserver tries to communicate with sesinetd via TCP port 1715: If the host firewall (firewalld in openSUSE) blocks ports 1714/1715, the connection fails with TCP connect failed.


E. Authentication and License Redemption (hkey / sesictrl)

hkey

An error may occur if there are previously destroyed containers or instances; SideFX servers hold those tokens as "phantom active sessions", blocking new authentication requests for security until manually cleared on the web. User persistence was also resolved with the --hostname flag during distrobox creation.

F. Application Launch

Once the license is registered:

- The program is launched by executing the houdini command in the terminal or selecting it from the desktop application launcher.
- During this first boot, Houdini automatically generates the user configuration directory in $HOME/houdiniXX.X/, where default preferences, color schemes, and panel layouts are stored.

#### HERE ARISES THE VULKAN ERROR (vkCreateInstance failed or GPU crash):

SideFX and NVIDIA assume that Houdini is installed on a native operating system (such as native Red Hat or Ubuntu). In that scenario, the official NVIDIA installer creates a Vulkan ICD JSON manifest pointing to the absolute path of the driver on disk. 

When running inside the container, the Vulkan loader in Houdini fails to initialize the graphics card, or when running 'vulkaninfo --summary' or trying to open Houdini 22, the software crashes displaying critical errors in the terminal such as "vkCreateInstance failed" or similar, because the /usr/lib64/ directory does not exist, causing the call to the GPU driver to crash instantly and fail to initialize.

#### 🔍 DIAGNOSIS

- Distrobox mounts your openSUSE Host root at '/run/host' inside the Debian container ('houdini') so that it can see the host's graphics drivers.
- The Symlink Puzzle: In openSUSE Tumbleweed, the configuration file '/usr/share/vulkan/icd.d/nvidia_icd.json' is usually an absolute symbolic link (symlink) pointing to another physical path on the system (such as '/etc/vulkan/...' or '/usr/lib/...').
- The Collapse: When the Vulkan loader inside Debian attempts to open the path '/run/host/usr/share/vulkan/icd.d/nvidia_icd.json', the kernel follows the symlink automatically. However, when resolving that absolute path, it searches for it inside the '/' of the Debian container instead of the '/' of openSUSE. Since that path does not exist in clean Debian, the system reports that the JSON file is broken or empty, leaving Vulkan completely "blind".

#### 🛠️ LOCAL BYPASS:

To solve this, a local Vulkan (ICD) configuration file is created within the container user space. Declaring a relative library path breaks dependency on the host's broken symbolic link and forces the system to look for the GPU in the memory injected by Distrobox.

Since Distrobox's `--nvidia` flag has already successfully injected the actual dynamic libraries of your RTX 5080 (`.so`) into Debian's paths, you do not need to touch the host or modify Podman mounts.

We only need to create a local Vulkan (ICD) configuration file inside the container's user space pointing directly to the shared physical library.

A. Create local Vulkan folder for your user inside the container

mkdir -p ~/.local/share/vulkan/icd.d/

B. Write the static ICD JSON pointing directly to the nvidia library
cat << 'EOF' > ~/.local/share/vulkan/icd.d/nvidia_icd.json
{
    "file_format_version" : "1.0.0",
    "ICD": {
        "library_path": "libGLX_nvidia.so.0",
        "api_version": "1.3"
    }
}
EOF

C. Force the Vulkan loader to use your local JSON, ignoring broken links from /run/host and making this change permanent every time you enter the Houdini box:

echo "export VK_ICD_FILENAMES=\$HOME/.local/share/vulkan/icd.d/nvidia_icd.json" >> ~/.bashrc


E. Apply changes immediately in current session

source ~/.bashrc


CONSOLE VERIFICATION:

vulkaninfo --summary

SUCCESS: The loader will immediately resolve the local JSON, find your NVIDIA GeForce RTX 5080 (Blackwell) card, and cleanly display the summary.

## STEP 7. SPECIFIC SOLUTIONS FOR RUNNING HOUDINI IN WAYLAND (VIEWPORT AND TRACKBALL RING).

We deactivate the modern interpreter **XInput2 (XI2)** and force the graphics backend to fall back to the classic XCB/X11 engine.

Required environment variables (in container's .bashrc):

export QT_QPA_PLATFORM=xcb
export GDK_BACKEND=x11
export QT_XCB_NO_XI2=1
export HOUDINI_USE_XINPUT=0

The first issue (3D Viewport visibility in Wayland):

When trying to run Houdini natively on host's Wayland compositor (openSUSE Tumbleweed), the 3D Viewport was not visible (stayed black or invisible) or the interface collapsed upon opening because SideFX lacks native Wayland support.

Injecting QT_QPA_PLATFORM=xcb and GDK_BACKEND=x11 forced Qt6 and GDK to work over the XCB/Xwayland compatibility layer, which immediately restored visibility and full rendering of the 3D Viewport.

The second issue (Kensington ring in Network Editor and Parameters):

Once the 3D Viewport was functional and 3D scrolling worked perfectly, the real problem with the Trackball appeared: the scroll ring did not work in the rest of Houdini's windows (especially in the Network Node Editor, Parameter Editor, drop-down lists, and inspectors).

Under Xwayland, Qt6's XInput2 (XI2) subsystem sends high-resolution fractional scroll events. Houdini's interface panels (like node and parameter editors) failed to interpret those XI2 events under Xwayland and ignored them.

Injecting QT_XCB_NO_XI2=1 and HOUDINI_USE_XINPUT=0 to turn off XI2 forced Qt6 to translate movement into traditional discrete X11 Button 4 and Button 5 impulses, restoring scroll functionality across the Network Editor, Parameters, and the entire app interface.
